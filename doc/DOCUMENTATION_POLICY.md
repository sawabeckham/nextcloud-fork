# Правила актуальности документации

Решение владельца от 01.11.2026: подробная документация — постоянная часть каждого проекта, общая для всех агентов.
Она хранится в Git вместе с кодом; история чата не должна быть единственным источником требований и решений.

## Перед изменениями

- Сверить рабочую ветку, незакоммиченные изменения, исходный ref и открытые PR. Не считать `main` автоматически самым свежим результатом.
- Прочитать индекс документации, актуальное состояние, передачу работы и инструкции репозитория.
- Проверить затрагиваемые факты по коду и конфигурации. Устранить найденное расхождение или явно отметить, что пока не установлено.

## Что обновлять в каждом законченном этапе

| Изменение | Документ |
|---|---|
| Назначение, возможности, начало использования | README |
| Структура, связи модулей, форматы данных, зависимости | Архитектура / карта файлов |
| Сборка, тесты, конфигурация, установка, обновление | Разработка / эксплуатация |
| Решение владельца, причина выбора, отвергнутые альтернативы | Решения / постоянный контекст |
| Поведение, совместимость, версия выпуска | CHANGELOG и описание версии |
| Результат этапа, проверки, известные ограничения | CURRENT_STATE |
| Незавершённая работа, следующий конкретный шаг | PROJECT_HANDOFF / TODO |

Адаптировать имена к существующей структуре: не создавать второй документ с тем же назначением. Подробности писать в тематическом документе, в состоянии и передаче оставлять ссылки. Старую историю не переписывать как текущие инструкции.

## Правила достоверности

- Версия берётся из принятого в проекте единственного источника. Документация фиксирует снимок с датой и исходным коммитом; перед новой задачей его нужно сверить.
- Разделять код, собранное приложение, установленную копию и production. Успешная сборка не означает выпуск или деплой.
- Для проверок указывать точную команду/сценарий, результат, дату и границы. Незапущенные проверки перечислять отдельно.
- Незавершённую задачу описывать так: что осталось, почему, затронутые файлы, что проверить, следующий шаг. Не заменять это обещанием «продолжить позже».
- Не публиковать пароли, токены, содержимое Keychain, `.env`, персональные данные и журналы с ними. Примеры конфигурации — с безопасными значениями.
- Документы обновлять до итогового сообщения и сохранять вместе с изменением кода. Документационные правки сами по себе не требуют увеличивать версию приложения.

## Перед передачей другому агенту

Проверить ссылки и пути; актуализировать состояние и следующий шаг; назвать активную ветку/PR и невыпущенные изменения.
Новый агент должен понять задачу по файлам проекта, не прося владельца повторить предыдущий чат.
Если документация не обновлена или часть фактов не проверена, прямо указать пробел, не называть документацию полностью актуальной.


## Уточнение03.11.2026: Unreleased и выпуск

Для этого крупного продукта изменения накапливаются. В metadata сохранять последний released номер, целевой указывать отдельно в Unreleased/CURRENT_STATE/PROJECT_HANDOFF. Сборки, compiled tests, PKG и установка до явной команды владельца отложены; фиксировать это как незапущенное, не как pass. Старые датированные указания о bump на каждую правку — история прежней политики. Новый комплект указан в INDEX; актуализировать затронутые документы, не дублируя историю целиком.
